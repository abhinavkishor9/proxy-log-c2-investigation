# Investigation Notes

## Investigation Summary

This investigation examined simulated HTTP C2 beaconing on a Windows endpoint using a controlled local HTTP listener and proxy-style request logging.

The purpose was to reproduce observable web communication in a safe environment and determine which artifacts could be used to investigate potentially suspicious HTTP beaconing.

The investigation followed an evidence-first approach. Controlled activity was separated from endpoint telemetry, and no malicious interpretation was assigned to the generated traffic without independent supporting evidence.

## Environment

The investigation was performed on:

- Host: `DESKTOP-9MMM37V`
- Operating System: Windows 11 Pro
- PowerShell: 7.6.6
- Sysmon: 4.91
- Wazuh Agent: `001`
- Workspace: `C:\ProxyLogC2Lab\Evidence`
- Controlled destination: `127.0.0.1:8080`

The investigation began by creating:

```text
C:\ProxyLogC2Lab\Evidence
```

Baseline artifacts were collected for:

- Host identity

- User context
- Network configuration

This provided environmental context before the controlled HTTP activity was generated.

## Controlled Destination

The intended controlled destination was:

```text
127.0.0.1:8080
```

The destination was selected so that the investigation could reproduce HTTP communication without contacting external infrastructure.

The activity was explicitly documented as:

```text
Purpose: Controlled local C2 simulation
```

## HTTP Listener

PowerShell `System.Net.HttpListener` was used to create a local HTTP server.

The intended endpoint was:

```text
http://127.0.0.1:8080/
```

The server returned:

```text
HTTP 200
OK
```

for received requests.

The listener captured:

- Timestamp
- HTTP method
- URI
- User-Agent
- Remote endpoint

These values were written to:

```text
Proxy-Requests.csv
```

## Traffic Generation

The investigation generated repeated requests to:

```text
/checkin
```

The primary pattern consisted of ten requests separated by approximately five seconds.

Additional requests were generated against:

```text
/checkin
/status
/config
/update
/checkin
```

with short delays.

This produced a controlled periodic pattern that resembles beaconing from a behavioral perspective.

The traffic was not malicious.

## Proxy Log Analysis

The generated request data was imported using:

```powershell
$Requests = Import-Csv "$EvidencePath\Proxy-Requests.csv"
```

URI frequency was examined with:

```powershell
$Requests |
    Group-Object URI |
    Select-Object Name, Count
```

User-Agent frequency was examined with:

```powershell
$Requests |
    Group-Object UserAgent |
    Select-Object Name, Count
```

The resulting evidence was written to:

```text
URI-Frequency.txt
UserAgent-Frequency.txt
Proxy-Requests-Review.txt
```

## Beaconing Analysis

The investigation considered the following characteristics:

- Repeated communication
- Regular timing
- Destination consistency
- URI repetition
- URI variation
- HTTP method
- User-Agent
- Response behavior
- Process context

The repeated `/checkin` requests created a predictable communication pattern.

However, this pattern was intentionally generated by the analyst and therefore cannot be treated as evidence of actual malware beaconing.

## Sysmon Network Investigation

Sysmon Event ID 3 was reviewed using:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = "Microsoft-Windows-Sysmon/Operational"
    Id = 3
} -MaxEvents 500 |
Where-Object {
    $_.Message -match "127.0.0.1"
} |
Select-Object TimeCreated, Id, Message
```

The results were saved to:

```text
Sysmon-NetworkConnections.txt
```

The investigation subsequently attempted to identify a specific Sysmon Event ID 3 record involving port `8080`.

## Port 8080 Correlation

A specific network event was expected to provide a timestamp that could then be used to search for nearby Process Create events.

The correlation approach was:

```text
Sysmon EID 3
    ↓
127.0.0.1:8080
    ↓
Network Event Timestamp
    ↓
±2 minute window
    ↓
Sysmon EID 1
    ↓
PowerShell
```

However, the network event variable returned null because the query did not identify a Sysmon Event ID 3 message containing the expected `8080` information.

The resulting PowerShell error was:

```text
You cannot call a method on a null-valued expression.
```

This occurred because `.TimeCreated.AddMinutes()` was called on a null event.

The issue was corrected by first validating that a matching network event existed before attempting timestamp-based correlation.

## Process Attribution Assessment

Because a specific `127.0.0.1:8080` Sysmon network event was not successfully established, the investigation did not claim a confirmed Process Create-to-network relationship.

The fact that PowerShell generated the HTTP requests is known from the controlled lab procedure.

However:

```text
Known:
PowerShell generated the controlled requests.

Not established:
A Sysmon EID 3 event can be definitively linked to that PowerShell process.
```

This distinction is important for DFIR analysis.

## Telemetry Limitation

The absence of a matching Sysmon Event ID 3 result should not be interpreted as:

```text
"No HTTP communication occurred."
```

The correct interpretation is:

```text
"No matching Sysmon network event was identified using the available query and telemetry."
```

This represents a telemetry or visibility limitation.

## Investigation Assessment

### Confirmed

- Investigation workspace created.
- Host and network baselines collected.
- Local HTTP listener configured for the intended controlled destination.
- Controlled HTTP requests generated.
- Proxy-style request logging implemented.
- Repeated `/checkin` requests generated.
- Multiple URI paths generated.
- URI frequency analysis performed.
- User-Agent frequency analysis performed.
- Sysmon Event ID 3 investigation performed.

### Not Established

- Real C2 infrastructure.
- Malicious HTTP traffic.
- External C2 communication.
- Malware execution.
- Compromise.
- Confirmed Sysmon process-to-`8080` attribution.

## Final Assessment

The laboratory successfully reproduced a controlled beacon-like HTTP communication pattern and demonstrated how proxy-style evidence can be analyzed for frequency, timing, URI patterns, and client information.

The traffic was intentionally generated against localhost and therefore does not constitute evidence of malicious C2.

The lack of a confirmed Sysmon Event ID 3 event for `127.0.0.1:8080` prevented definitive process-to-network attribution.

The final assessment is therefore:

> **Controlled HTTP beacon-like activity confirmed. Real malicious C2 not established. Process-to-network attribution through Sysmon remained inconclusive.**
